## 问题清单

### B01 · P1 · 零现金被替换成全部净值（已复现）

位置：`backend/opportunity/ranking.py:261–262`。

`float(state.get("cash") or equity)` 将合法的 `0` 当作缺失。净值 10,000、现金 0 的账户，输出当前仓位 0%、可用空间 60%、最多新开 2 只；正确结果应反映 100% 已有仓位。净值本身为 0 时也会被替换成 1,000,000。

修复：区分 `None`、缺失与零值；校验有限数和合法范围。现金不足时禁止形成可执行的新仓建议。

验收：现金为 0、净值为 0、极小现金、负值、NaN/Infinity 各有明确结果，不默认恢复成百万账户。

### B02 · P1 · 显式 0 股或负数量触发全仓买入（已复现）

位置：`backend/paper/engine.py:235–237`、`backend/dashboard/static/index.html:751`。

仅在请求数量大于 0 时限制买入量，其余情况按全部可用现金买入。10,000 元账户请求 0 股，实际成交 900 股。前端空数量也主动发出 `quantity: 0`，因此正常表单操作会触发该路径。负数量同样不被拒绝；卖出中的非正数量也会落入全卖分支。

修复：明确“未指定”与“显式非法数量”的区别；手动买单要求填写正整数和整手数量，任何非正值返回 400。全仓/清仓作为显式操作。表单禁止重复提交。

验收：0、负数、非数、空输入不触发交易；不足一手与非整手给出准确提示；拒单展示拒绝原因。当前前端会把 REJECTED 订单也显示成“已成交”，需要一起修正。

### B03 · P1 · 模拟盘没有执行涨跌停和停牌约束（已复现/代码确认）

位置：`backend/api/v1.py:846`、`backend/paper/engine.py:158`。

手工接口直接将用户填写的价格送入账户执行器，没有读取当日价格限制、停牌状态或标的资格。样例供应商明确给出涨停价 11 元，提交 11 元买单仍返回 `201 Created / FILLED`。卖出同样没有跌停拒绝逻辑。README/验收报告声称的规则在此实际入口未落地。

修复：共享成交校验器，由模拟盘和回测调用；校验股票身份、交易日、报价日期、涨跌停、一字板和停牌。缺少成交验证数据时明确不可验证；历史重放使用独立账户。

验收：相关边界从 HTTP 到最终账户状态都覆盖，拒单不改变现金或持仓。

### B04 · P1 · T+1 错误锁住旧持仓，交易日期又可任意填写（已复现/代码确认）

位置：`backend/paper/models.py:38`、`backend/paper/engine.py:348`、`backend/api/v1.py:849–852`。

持仓只保存最后一次买入日期。前一天买入 100 股、今天再买 100 股，今天卖出旧的 100 股会被拒绝。默认交易日取历史库最后日期，缺省甚至回到 `20240103`，没有使用实际交易会话。传入不同日期还可绕过简单的日期相等判断。

修复：按批次或“可卖数量/今日买入数量”管理结算；实盘式模拟账户使用受控交易日期，回放账户允许历史日期但保持单调顺序。

验收：加仓后旧仓可卖、新仓不可卖；重启不改变可卖数量；逆序日期、非交易日和历史回放不会污染当前账户。

### B05 · P1 · 风控使用成本估值，成交后交易计划仍使用旧账户（已复现/代码确认）

位置：`backend/api/v1.py:380、396、714、729`、`backend/paper/engine.py:191`。

API 调用 `snapshot()` 不传价格，因此用持仓平均成本估值，不能反映浮亏或浮盈。复现中成本估值 10,099.37，按 5 元报价估值为 9,599.07。`_trade_plan` 的缓存键只有日期，即使成交改变现金/持仓也会保留旧计划至 TTL 到期；本次样例中缓存现金与实际现金相差 1,000.30 元。`peak_equity` 也没有持久化实际历史峰值，无法可靠计算账户回撤。

修复：统一账户估值服务，记录报价来源/日期和持久化峰值；给账户引入版本号，将依赖账户的缓存与市场缓存分开。成交、交易记录与配置更新后即时刷新相应结果。

验收：交易后无需等待 TTL，持仓页、风险、计划与 AI 一致；报价缺失与过期明确标注；下跌会改变净值和回撤。

### B06 · P1 · 盈利成交没有进入个人画像，观察记录也被统计成交易（已复现）

位置：`backend/paper/engine.py:294–325`、`backend/profile/engine.py:50–67`。

模拟盘记入日志的 `result` 仅有价格和数量；画像期待 `pnl/return_pct/holding_days`，缺失则全部当作 0。样例完成一买一卖、实际盈利 99.37 元，画像却显示累计盈利 0、交易数 2、盈利交易 0。画像遍历全部日志而不区分 BUY、SELL、HOLD、WAIT、MISSED_SIGNAL；十条观察记录也可能满足“样本充足”。

修复：区分决策事件、成交和已平仓交易；记录成本、费用、已实现盈亏与持有期，按完整交易或明确的分批平仓口径统计。缺失结果应为未知，不替换成 0。画像回撤需要账户净值序列，不能从初始值 1 加人民币盈亏推算。

验收：一轮交易只计一次已完成交易；买入/观察不算盈利样本；分批买卖和费用可与账户账本核对。

### B07 · P1 · 回测止损绕过跌停限制，并在收盘确认时按同一收盘价成交（已复现/代码确认）

位置：`backend/backtest/ashare_engine.py:239–289`。

保护性退出独立执行，没有经过普通 SELL 的跌停检查。复现中买入价 10 元，次日全部 OHLC 为跌停价 9 元，系统仍以 9 元卖出。它还用当日收盘价判断止损/止盈，再以同一个收盘价成交，没有体现信号确认后的执行时序。

修复：所有退出统一走成交检查。日线方案可在收盘确认后排队至下一交易日开盘；若采用日内委托，需要可支持该假设的数据。涨跌停无成交时保留待执行订单。

验收：跌停锁死不会凭空退出；普通卖出和止损使用相同约束；执行日期/价格假设可追溯。

### B08 · P1 · 回测逐笔盈亏遗漏买入费用，加仓覆盖首次建仓信息（已复现/代码确认）

位置：`backend/backtest/ashare_engine.py:183–186、220、273`。

逐笔 PnL 只扣卖出佣金和印花税，买入佣金已从现金扣除但没进入交易 PnL。全部平仓样例逐笔亏损 -20,043.28，账户变化 -20,102.98，差额 59.70 元为买入佣金。每次加仓还覆盖 `open_trades[ts]`，再以最后一次入场价和日期计算整个持仓的盈亏与持有期。

修复：使用批次成本或完整的加权成本账本，分配全部交易费用，保留结算日期。停牌/缺少当日 bar 的持仓仍应按明确的最近有效价格估值；目前收盘估值循环会遗漏无 bar 的仓位。

验收：所有持仓平掉后，逐笔盈亏之和等于账户变动；加仓、减仓、停牌及费用都能对账。

### B09 · P1 · 回测界面的“胜率”实际是账户上涨天数占比（已复现）

位置：`backend/backtest/metrics.py:68–70、113`。

传入已平仓交易日志后，计算器更新了交易数和盈亏比，却没有更新胜率。账户连续上涨但唯一已平仓交易亏损的样例仍输出胜率 100%。未平仓浮盈可以掩盖已完成交易的亏损。

修复：分别输出交易胜率与账户上涨日占比，无平仓样本时交易胜率为 null；明确年化期间与夏普计算口径。单个区间收益除以年化波动的现有夏普算法也应审定。

验收：交易胜率只由已平仓有效结果决定；界面字段名与统计口径一致；无样本不显示 0% 胜率。

### B10 · P1 · 历史 ST 涨跌停价使用未来数据（已复现）

位置：`backend/data/providers/history.py:127–166、280`。

`_recent_max_moves()` 查询全库 `MAX(ABS(pct_chg))`，没有截至请求日期的限制，再据此校正所有历史日期的 ST 状态。样例历史 ST 日的涨停价原为 10.50；新增后一天 10% 涨幅数据并清缓存后，同一历史日变成 11.00。历史信号、连板计数与成交判断会随未来数据改变。

修复：保存按日期生效的证券状态/规则，不用未来波动推断历史状态；至少让任何启发式只读取 T 日以前信息并标注不确定性。当前 `_detect_lookahead` 仅检查信号日期是否出现在行情中，无法证明没有未来数据泄漏。

验收：添加 T+1 及之后数据不能改变 T 日的限制、梯队和信号；ST 变更区间按实际生效日处理。修复后重新生成依赖这些字段的研究结果。

### B11 · P1 · 补数失败停止重试，部分全市场数据被当成完整数据（已复现/代码确认）

位置：`backend/data/auto_ingest.py:22、108–128、54`。

异常路径 `finally` 仍把当天加入 done；返回 `failed` 的结果也不检查。样例首次供应商异常后，下一轮返回 False，只请求过一次。每日达到 100 行就不再补，而全市场有五千余只；一次部分成功后会长期缺数据。补数失效逻辑未调用 `HistoryProvider.clear_cache()`，旧日线窗口和涨停缓存仍可能继续使用。另有 10 个交易日回溯上限，长期未启动时不能修复更早缺口。

修复：持久化任务状态与失败代码，校验覆盖率；成功完成才写 done，失败按退避策略重试。所有读取/写入使用 runtime 对应数据库，补数后清除供应商与派生缓存。关闭日也应允许补历史缺口。

验收：完全失败、部分失败、写入中断、重启、停用超过 10 个交易日都可恢复；不是只靠行数阈值判定完整。

### B12 · P1 · AI 使用新建空账户，行情日期和规则也与正式接口不同（代码确认）

位置：`backend/ai/context.py:73–74、114–128`、`backend/api/v1.py:876`。

`build_context` 创建没有 `state_path` 的 `PaperTradingEngine()`，每次得到百万现金、空持仓，忽略 API 的 runtime 账户。AI 又独立计算市场/情绪而没有复用 API 的梯队和基准日期逻辑；快照路径只判断请求日期不早于历史最后日期，没有校验快照 quote_time 是否对应请求日期。

修复：向 AI 注入统一决策上下文，复用同一账户、同一行情基准日期和同一引擎结果。统一测试/demo 数据标记。开放式 LLM 尚未实现，即使有 Key 也不应返回 `ai_available=True`（`backend/ai/agent.py:184`）。

验收：持仓、现金、风险和情绪在 AI 与相应 API 一致；旧快照不会冠以当前日期；AI 能力状态按实际后端可用性报告。

### B13 · P1 · 并发初始化可创建多个账户实例（已复现；交易并发另需测试）

位置：`backend/api/app.py:25–29、68、108–120`。

服务使用 ThreadingWSGIServer，后台补数线程与首批请求会调用无锁 `_get_runtime()`。双线程样例实际返回两个不同实例，可能从同一个磁盘状态创建不同账户。模拟盘的执行、持仓更新和持久化也没有事务锁，后续需要对并发订单做完整验证。

修复：启动前完成本地初始化或使用一次性初始化锁；为写操作提供账户事务、订单幂等键。静态首页和 health 应在路由匹配后直接返回，当前先初始化 runtime/执行 dispatch，可能受到交易日历和数据源调用拖累。

验收：首屏并发请求只有一个 runtime；并发重复单只成交一次；初始化与网络故障不会阻断静态首页和基本存活检查。

### B14 · P1 · 状态写失败仍报告成交成功，账户与日志非原子更新（已复现/风险）

位置：`backend/paper/engine.py:75–111、291、294–330`、`backend/journal/trades.py:108`。

JSON 文件直接覆写，遇到 OSError 静默忽略；日志失败也被吞掉。故障注入中写盘失败，订单仍是 FILLED、状态文件不存在。进程在覆写期间退出存在截断风险，下一次 `load()` 读不出时静默返回默认百万现金。账户先保存、再写日志，无法保证两个状态一致。

修复：优先将订单、现金、持仓与审计事件纳入 SQLite 事务；若继续使用 JSON，需要临时文件加原子替换、备份与明确错误反馈。恢复失败时停止交易并提示恢复状态，不能静默创建新账户。

验收：磁盘失败、日志失败、进程中断及重启不会丢失或重复成交；持久化失败不能显示成功。

### B15 · P2 · API 输入校验和错误语义不完整（代码确认）

位置：`backend/api/v1.py:52–59、763、814、846`。

非法 JSON 被替换成 `{}`，回测会按默认参数开始执行；JSON 数组、非法浮点数、无效价格等可能走到未捕获异常并返回 500。未知策略静默回退 ma_cross，却把传入的不存在策略 ID 存到结果，造成策略身份错误。没有请求大小上限和完整的日期/标的/action 校验。

修复：定义请求 schema，有限数、日期格式/范围、标的、枚举、策略 ID 都先校验；输入错误返回 400/422。回测任务保存真实策略身份与配置版本，长任务使用任务状态接口。

验收：错误请求不改变账户、日志或创建回测；同类错误有一致状态码和可读提示。

### B16 · P2 · 生产数据仍可能降级到 Fixture，全市场资格检查不足（代码确认）

位置：`backend/api/runtime.py:93–131`、`backend/data/providers/fallback.py:23–43`、`backend/backtest/ashare_engine.py:374–389`。

无本地库时 fallback 链含 Fixture，且 data_timeliness 固定来自链首，未记录实际命中的供应商。按不同表独立降级还可能混用来源。全市场校验仅在选择历史库时检查累计代码数，CSI300 CSV 分支未实施同样资格检查。回测 `_stocks_only` 在筛选结果为空时返回原始数据，意味着仅请求指数序列时可能又把指数作为可交易标的。

修复：生产模式排除 Fixture；demo 模式显式开关、显示标记。每个结果携带实际数据来源、覆盖率、日期与可用能力；不足全市场覆盖时禁止发布全市场结论。股票过滤为空应报无可交易股票。

验收：网络全部失败时生产接口返回数据不可用；只有指数数据时回测不能成交；测试样例不会作为历史真实行情展示。

## V1.1 建议范围与顺序

建议把 V1.1 定义成“交易规则、数据一致性与运行可靠性版本”。先完成可对账的基础，再开展策略研究或分钟数据接入。

| 阶段 | 工作 | 主要问题 | 完成标准 |
|---|---|---|---|
| 1 · 账户与成交 | 请求校验、共享成交检查、批次 T+1、事务账本、幂等、估值 | B01–B06、B13–B15 | 现金+持仓净值可对账；拒单不改状态；故障可恢复 |
| 2 · 数据与上下文 | 任务化补数、覆盖率、数据来源、按日期证券状态、缓存版本、AI 统一上下文 | B10–B12、B16 | 同一日期可重现；补数可恢复；各页面与 AI 口径一致 |
| 3 · 回测正确性 | 退出时序、统一成交规则、完整成本、已完成交易统计 | B07–B10、B16 | 逐笔盈亏等于账本变动；未来数据不改变过去结果 |
| 4 · 发布体验 | 一键启动、停止脚本、运行状态、错误提示、手机验收 | B02、B13、B15 | 服务未启动有明确指引；页面显示数据与任务状态；拒单原因可见 |

### 可以优化的地方

1. **启动和运维**：增加 Windows 一键启动/停止脚本，检测端口占用，明确区分 liveness 与 readiness；为日志配置 UTF-8、轮转和结构化任务摘要。刚才网页不可访问的直接原因是服务未运行，启动便利性值得纳入版本。
2. **并发与性能**：TTLCache 增加同键 single-flight，避免首屏并行请求重复计算；缓存键包含数据版本/账户版本。限制历史窗口、列表长度和回测资源，不一次返回无限长日志。
3. **模块结构**：拆分大型 `api/v1.py` 为行情、决策、账户、研究路由；前端单 HTML 中的表单与数据加载逻辑按模块拆分。先建立共享服务，避免不同入口各算一遍不同规则。
4. **SQLite 连接**：当前多处 `with sqlite3.connect(...)` 只提交/回滚，不确保关闭连接；复现脚本在 Windows 清理临时目录时遇到文件占用，垃圾回收后解除。建议显式关闭连接，按实际并发测量是否需要 WAL、busy_timeout 和索引。
5. **数据能力展示**：统一显示 requested_date、basis_date、quote_time、source、coverage、missing_fields；成交额缺失与行业/题材差异持续保持明确标记。
6. **研究流程**：修复成本、成交和历史状态后重算原报告；冻结样本与配置，做时间分割、对照和敏感性分析。先完成计算正确性验收，再评价策略收益。
